## Diagnosis and fix scope

See audit/media-acceptance/2026-09-23-tm221-window-burst-diagnosis.md for original uploaded evidence. The current uploaded batch selected 20 jobs, and all twenty failed with controller_lease_lost. First failure was 1 ms after batch start; subsequent failures were 3.502–4.009 seconds apart. This is a controller dispatch defect, not evidence of twenty parallel successful captures or publisher missing-image failures. The exact production code and actual resume callback reproduced the same 20-launch/20-failure sequence with mocked Tampermonkey APIs. A resume click during startup can delete the running lease; the logs alone do not establish who deleted this particular lease.

Installed Bridge/controller revision is now 2.2.21. Capture protocol remains 6.2.20 deliberately for deployed Worker intake and successful-image checkpoint compatibility. No Worker code, media storage, literature data, quarantine epoch or frontend UI was changed by PR141.

The updated controller does not delete live leases from resume/start/failure-reset menus; checks ownership before every launch; stops the whole batch on lease loss; invalidates only its own active job; awaits any asynchronous tab handle and confirms tab.closed after close() before opening another page. If closure cannot be confirmed, further launching stops. Fatal infrastructure stops are latched against automatic timer retries until explicit resume. Historic controller_lease_lost results are not treated as publisher failures requiring cooldown. Packaging now disables the old viewport queueDoi/pump/scan collector when the bound mainline is active.
