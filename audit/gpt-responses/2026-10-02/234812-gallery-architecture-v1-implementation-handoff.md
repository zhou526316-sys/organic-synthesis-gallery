## 一、整体架构：保留现有平台，重新明确各层职责

**不需要整站重写，也不需要明天引入云电脑、换模型或另建一套发布系统。**我的建议是在现有 GitHub Pages、Worker、D1/R2 和 Tampermonkey 上完成以下分层。

| 层 | 负责什么 | 不再负责什么 |
|---|---|---|
| **Canonical 文献目录** | 保存唯一、规范化的公开文献事实，按月和容量分片 | 不在浏览器中临时合并多套互相覆盖的数据 |
| **生命周期层** | 用同一规则计算最近三个月与历史区 | 不复制、搬迁或删除到龄 DOI |
| **定位与检索层** | DOI 定位、全库搜索、收藏和分享深链 | 不要求首页先加载全部历史记录 |
| **统一资产目录** | 登记每篇已取得、已验证、已发布的 TOC、正文图、Evidence 和摘要 | 不把“暂存存在”当成“已经上线” |
| **活跃任务层** | 调度当前缺口、租约、重试、历史补录和明确修复 | 不反复扫描或抓取全部历史论文 |
| **发布与验证层** | 沿用固定槽链，记录每次发布及线上验证证据 | 不把最新审核未闭合误判为上一版发布失败 |
| **用户与统计层** | 保存用户状态、阅读去重和物化统计 | 不让附加功能失败阻断静态文献浏览 |

这些是**逻辑模块，不是七个新服务器**。第一阶段主要改数据契约与读取方式，复用当前已经能工作的执行环境。

## 二、三个月规则：这次固定成一个无歧义的定义

建议采用最初讨论的“滚动三个月”口径：

```text
D = 北京时间今天
C = D 向前减 3 个自然月；不存在的日期钳到目标月最后一天

Hot：已公开且 C ≤ firstOnlineDate ≤ D
Archive：已公开且 firstOnlineDate < C
```

因此，**明天 10 月 3 日，cutoff 是 7 月 3 日：7 月 1、2 日进入历史区，7 月 3 日仍属于热区。**这只是日期规则，不改变这些论文是否被收录。

这里必须修正前几版的一处不一致：**不能同时把“今天减三个月”和“论文日期加三个月”当成两个权威公式。**自然月运算存在月底钳位，两者不一定互为逆运算。例如，2027 年 2 月 28 日加三个月是 5 月 28 日，但 5 月 31 日减三个月仍是 2 月 28 日。按本版口径，这篇论文到 5 月 31 日仍在热区。citeturn283963search16

实现上只保留一个共享生命周期函数，前端、构建器和任务领取都调用它。轻量 `lifecycle manifest` 保存日期、规则版本、目录版本及集合摘要，但它只是派生结果，不能成为第二份文献数据库。

**跨午夜要更新视图，不必等下一次 08:00/18:00 文献发布。**页面休眠后恢复也要复核日期；无法确认可信日期时显示最近确认状态，不能依据错误电脑时钟自动清理数据。

另外，三个月仅限制默认展示和常规主动维护。**尚未闭合的语义审核、范围纠错、晚发现旧论文和明确历史修复可以继续处理，但不能因此把旧论文重新变成 Hot。**现有协议本来就要求 pending backlog 即使移出窗口也继续保留。fileciteturn66file0L2-L2

## 三、文献数据：一份事实源，两个视图，三个入口

### 一份事实源

由构建程序将获准的生产输入统一生成 Canonical Catalog。初期仍沿用当前生产写入口，Canonical 先作为影子输出；验证无损后才切换前端读取。

每篇至少保留 DOI、中英文标题、作者、期刊、首次在线日期、收录日期、分类、原文地址、记录版本和审核来源。

**`firstOnlineDate` 决定冷热；`addedDate` 表示何时加入 Gallery。**12 月补进一篇 7 月文章，应该进入 7 月历史数据，并在“最近补录”里显示，而不是修改发表日期使它进入热区。

建议的文件形式是：

```text
catalog/current.json
catalog/releases/<版本>/manifest.json
catalog/shards/2026/07.<内容哈希>.json
catalog/shards/2026/08.<内容哈希>.json
catalog/locator/<分片>.<内容哈希>.json
search/<分段>.<内容哈希>.json
summaries/<分片>.<内容哈希>.json
```

旧月份不会因为每天过了一天而重写。历史纠错或补录可以产生新版本；只有**日期被正式纠正**时才可能调整月份位置，并同时更新定位索引。

### 两个视图

**Hot 首页**保持现在的完整体验，只按需读取最近三个月的数据。

**Archive 历史区**按月份或搜索结果读取，TOC 保留；正文图、高清图和摘要按需取得。归档不是删内容，也不是废弃入口。

### 三个入口

普通浏览走月份分片；关键词搜索走分段搜索索引；分享、收藏和精确 DOI 查询走 **DOI Locator**。

Locator 只回答“这个 DOI 在哪一个分片、哪个记录版本”，不复制整篇论文。以后 `?doi=` 指向历史论文时，直接打开该篇并保留定位高亮，不需要把整个历史库下载下来，也不把它塞回 Hot。

**全库搜索必须仍然是真正的全库搜索。**尚未加载完历史搜索段时，可以先显示已找到的结果，但必须标明进度；不能把“只搜了当前页面”报成“全库没有”。分片解决按需加载，不会让无条件全库搜索自动变成零成本操作。

## 四、前端与抓取器之间，必须增加一道明确边界

当前 `src/main.ts` 仍会把筛选结果整体 `map/join` 写入 DOM；全站 DOI registry 也由浏览器的 `papers` 数组生成。fileciteturn68file0L2-L2

这意味着明天改成按需加载后，有一个很危险的连带问题：

> **浏览器只加载了几十篇，不代表网站只收录了几十篇。**

因此，**Tampermonkey 绝不能再用当前 DOM 或已加载卡片集合推断全站文献成员资格。**它必须读取独立、带版本和完整性标记的正式 registry／成员查询。屏外、未加载、已归档与正式撤下，必须是不同状态。

前端最终建议真实 Card DOM 控制在约 **60–100 张**，图片只在视口及有限邻近范围请求。这个数字是初始测试目标，不是所有设备通用的硬限制。`IntersectionObserver` 可以用于接近视口时触发加载。citeturn783444search3

但**明天不必把读取架构和整个虚拟列表同时重写**。先让 Hot/Archive 数据路径正确，现有卡片组件保持；窗口化随后独立验收，这样出现滚动、分享或弹窗问题时更容易定位。

## 五、媒体与摘要：统一“已经有什么”，再计算“还缺什么”

**资产目录与任务队列必须分开。**

资产目录登记 DOI、资产类别、原始来源、内容哈希、尺寸、采集批次、验证结果和公开版本，明确区分 `captured → validated → published`，以及隔离状态。Worker 暂时查不到的结果应是 `unknown`，不能自动变成“缺图”。

活跃任务只从这些事实推导。当前 `media-jobs.js` 的领取条件主要还是 mode、state、next_retry_at 和 priority，尚未体现这套三个月资格规则。fileciteturn69file0L2-L2

### 抓取仍以一个 DOI 为工作单元

调度器决定下一篇打开哪篇；进入出版社页面后，当前能取得的 TOC、正文图和 Evidence 尽量一次完成，各项分别核验与回执。

优先级继续是**最新收录／更新批次优先，再按你确定的期刊顺序**。失败跳过继续；“立即开始”重新建立最新优先顺序，但不抹掉已核验资产，也不绕过出版社访问验证和限流。

普通 Archive 停止持续主动重试；最近补录可给一个短期首次补全窗口，明确修复可重新激活。正在进行的合法任务可以完成，结果写入历史资产；缺图不能延长 Hot。

**官方 TOC 与 Figure 1 永远分开。**既有 TOC／正文同批发布规则继续保留；媒体不足仍不阻止已获准的文献卡片发布。fileciteturn66file0L2-L2

### 摘要不能继续依赖全历史对象枚举

本轮重新确认，`scheduled-summary-handoff.js` 的待处理枚举仍最多读十页、每页一千个对象。这会在规模增长后造成候选发现不完整。fileciteturn73file0L2-L2

目标是建立 **Active Evidence Index**：日常摘要任务只查询需要处理的 DOI 与证据版本；R2 保存完整证据字节。全库对象对账可以低频、游标续跑，但不能把“扫描到上限”报成“全部完成”。

公开摘要按月或容量分片，并绑定对应 Evidence 哈希。只有摘要证据就按摘要总结，不假装读过全文。新增一篇无关论文，不应导致所有历史摘要失效。

## 六、发布：沿用现有链，不另外再造一个控制中心

当前仓库已经明确采用：

```text
可信 prepublish gate
    → 现有固定槽 writer
    → main 上的 Pages workflow_run
    → 线上 delivery receipt
    → finalizer
```

它已经包含当前 main 重核、固定槽执行界限、输入指纹及线上验证要求。**明天应保留，不重新设计一套平行 dispatcher。**fileciteturn71file0L2-L2

需要补强的是两个边界。

**第一，发布版本完整性与最新审核闭合分开。**前者核对同一个冻结版本的 review、dataset、marker 和 delivery receipt；后者检查最新 discovery、pending、carryover 和 `verifiedThrough`。下一轮发现新论文，不能反过来让上一轮正确部署的版本变成“发布失败”。

**第二，各域独立版本化，但兼容关系明确。**Catalog、媒体、摘要可以分别更新。搜索和 Locator 对应明确的 Catalog 版本；摘要和图片还要核对对应 DOI 的记录／证据版本及撤下状态，不必每新增一篇就重建全部派生物。

分片和对象先准备、校验，再公布引用它们的 manifest；浏览器锁定这一份 manifest，不自行拼接“各文件的最新版本”。不过，不能把 GitHub、D1、R2 和 CDN 想象成一个跨系统原子事务；对象存储一致性与外层缓存一致性也是不同问题。citeturn783444search0

**线上验证必须发生在实际部署之后。**`latestVerified` 是验收和恢复锚点，不应被实现成“必须先在线验证才能第一次上线”的循环依赖。

## 七、存储、用户数据和回滚底线

**Git/Pages 保存轻量公开阅读数据；R2 保存长期大对象；D1 保存可索引的动态状态。**

Pages 不应每次重新处理所有历史正文图片。当前媒体镜像程序仍从全部生产输入建立 DOI 集，后续必须改成有边界的 Hot 媒体构建。**但必须先确认历史图片已由 R2 正确承接、旧链接仍可用，再停止 Pages 镜像，不能先删后搬。**fileciteturn70file0L2-L2

原始全文、私有 Evidence、认证会话和密钥不得进入公开静态包。大型图片和 `.b64` 运输载荷不再长期新增到 Git；第一批改造不进行 Git 历史重写。

用户状态最终按 `(user_id, doi)` 保存，收藏里只保存身份和个人状态，不复制另一份论文事实。当前用户库仍有约 1.5 MB 整包上限，但明天应先保留兼容接口，逐行迁移另批实施。fileciteturn74file0L2-L2

统计改成物化汇总。不过，**原始 PV 可以设保留期，永久 DOI＋IP 去重标记不能仅保留总数后删除**，否则同一 IP 回访会再次计数；每日 UV 相加也不能冒充累计 UV。

还有一点要修正此前的措辞：把统计拆到另一个 D1 数据库，可以改善逻辑隔离，但**不能认为同一账号的免费日额度因此独立了**。Cloudflare 的免费日读取／写入超额是账号层面的限制。citeturn283963search2

回滚时优先关闭新读取或新队列适配，**不要把整个 main 重置到昨天**。新收录论文、用户写入、累计阅读和已确认撤下记录都不能随 UI 回滚丢失。旧数据包若会复活已撤下论文，就不能直接用作恢复版本。

## 八、明天具体做什么：先完成一个可回滚的版本

### 第一阶段：影子 Canonical＋共享生命周期

重新固定当时最新生产快照，生成 Canonical、Locator 和三个月分组，但不改变线上读取。

验收是**完整 DOI 集和关键字段一致**，而不是“脚本退出码为零”。必须包含月底、闰年、跨午夜、晚补录、日期纠正及已撤下 DOI 的测试。

### 第二阶段：切换 Hot／Archive 读取

让首页默认只读最近三个月，历史区、全库搜索、收藏及 DOI 深链仍能找到旧论文；保持当前写入和发布链，保留回退开关。

**这一阶段最适合作为明天的首批正式交付。**先完成数据读取与生命周期，不同时迁移账号数据库、更换模型、重写所有卡片组件。

### 第三阶段：资产对账与任务资格

先做影子资产目录，区分真实缺失、已发布和未知状态；随后单独启用生命周期资格适配。验证屏外论文不被误删、Archive 不持续普通重抓、新增仍优先、旧浏览器迟到结果不能覆盖新任务。

Active Evidence Index、摘要分片、Pages Hot-only 媒体、DOM 窗口化、用户拆表和统计物化继续分批实施。**这些属于完整目标，但不应挤进明天一个巨大 PR。**

你前面提出的“单入口脚本”也纳入目标：未来用一个入口调用现有模块，规则与案例版本化，审阅后端可替换。明天默认仍使用现有审阅方式，不额外绑定 OpenAI API，也不把模型替换与架构迁移混为一次实验。

## 九、必须通过的验收与停止条件

首批上线至少应证明下面这些结果：

| 检查 | 必须达到的结果 |
|---|---|
| 文献完整性 | 归档前后全库 DOI 不丢失、不重复，撤下不回流 |
| 生命周期 | 10 月 3 日的 7 月 1、2 日记录属于 Archive，7 月 3 日仍 Hot；月底规则统一 |
| 历史可达性 | 旧分享、收藏、搜索仍能找到正确论文 |
| 队列成员资格 | 页面没渲染的论文不被当成删除；缺图状态与资产事实一致 |
| 发布 | 08:00/18:00 原链继续工作，架构更新不越权新增文献 |
| 故障降级 | D1 失败不使静态文献白屏；单个历史分片或图片失败不拖垮全站 |
| 回滚 | 能退回兼容读路径，不丢新增、用户数据或撤下记录 |

性能先以**真实 DOM 约 60–100、分片压缩后约 1–2 MB、正常 Pages build 目标 5 分钟内、超过 7 分钟预警**作为待测预算，不是已经实现的指标。GitHub 当前规定 published Pages 最大 1 GB、部署超过 10 分钟会超时，因此不能把平台极限作为正常工作目标。citeturn283963search0

**这版架构最核心的实施原则是：先保证“旧文献不丢、旧功能不断、发布链不破”，再逐层限制加载量、任务量和构建量。**明天先完成“共享生命周期＋无损 Catalog 读模型＋可回滚 Hot/Archive”，其余按独立验收继续。

本轮已生成完整实施规格，并核对了六组日期契约算例；没有执行生产改造、新架构端到端测试或压力测试。文件中的预算与阶段门仍需在实施中验证。
