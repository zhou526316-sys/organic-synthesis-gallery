**可以整合成一个“单入口的文献更新程序”，而且不必绑定云端大模型。但“把流程封装起来”和“把模型的判断能力变成普通脚本”是两件不同的事。**本地运行模型是可行的；例如 Ollama 支持关闭云端功能，llama.cpp 支持在自有硬件上运行模型。是否能达到你当前文献审核的要求，需要单独验证。citeturn827080search0turn827080search1

对你的 Gallery，我更建议做成：

> **一个可独立启动的运行包＋一套版本化规则与案例＋一个可替换的审阅后端。**

这样可以不再依赖“每次由聊天窗口临时组织整个工作”，也不必把网站永久绑定到某一家模型服务。

## 二、为什么不能只用一个规则脚本替代全部判断？

因为你的标准不是“题目出现 synthesis、catalysis 就收录”。当前契约要求区分：文章的主要贡献究竟是可推广的有机制备方法，还是材料性能、机理研究、蛋白工程，合成仅仅是其中的制样步骤。它还明确禁止单凭关键词、产物属于有机物、例子数量或“有底物拓展”一句话就决定纳入。fileciteturn54file0L2-L2

举一个示意例子：两篇论文都出现“催化剂、醇氧化、底物拓展”。第一篇的核心可能是电极材料的结构与能效，第二篇的核心可能是具有一般适用性的选择性合成方法。脚本可以提取这些词，但仅凭这些词不能完成你要求的区分。

这里还有一个特别重要的区别：**校验器通过，不代表科学判断一定正确。**

当前审核校验器会检查候选是否全部覆盖、DOI 是否重复、证据字段是否存在、理由长度是否达标、两遍结论是否对应、来源检查是否齐全等。这些检查非常必要，但它们并没有重新理解论文、证明每一句审核理由都被原文支持。fileciteturn59file0L2-L2

因此，把现有校验器和抓取脚本拼在一起，仍然不能自动补出中间那一步的语义判断。

但这也**不等于只能用云端大模型**。判断可以由本地模型、经过验证的专用分类模型，或者人工承担。我的建议是：先保留可替换的判断接口，不预先假定某个小模型或纯规则一定达到要求，也不把大模型回答当作绝对正确。

## 三、“单个脚本”“技能包”和“独立程序”有什么区别？

**单个脚本**主要统一执行入口。例如你只启动一次，它就依次完成发现、准备证据、等待审核结果、校验、提交和核验。它内部仍然可以调用多个模块。

**技能包（Skill）**主要统一“如何做这件事”。以 OpenAI 官方的技能结构为例，它通常是一个 `SKILL.md`，配套脚本、参考资料和模板。它能够保存你的工作方法，但仍需要一个执行它的智能体或程序；Skill 本身不是模型。citeturn895810search0turn895810search21

**独立运行包**则要把两者结合，并补齐依赖、配置、状态保存、授权接口、错误恢复和测试。它可以对外只有一个启动入口，但内部保持模块化。

**对于你，我推荐第三种。**用户操作可以是“一个入口”，维护上不要变成“一个几万行、任何修改都牵动全局的文件”。

尤其要注意：聊天里可调用的联网搜索、GitHub 连接器、浏览器工具，并不会因为把提示词复制进脚本就自动出现。移植时必须明确每项能力对应哪个实际接口或执行程序，权限和凭据也要单独配置，不能塞进可分享的脚本。

## 四、在你不使用 OpenAI API 的前提下，有三条路线

### 路线 A：统一脚本＋现有 ChatGPT 审阅

脚本负责确定性的环节，将候选、证据和规则整理成固定格式，通过现有正式交接路径交给 ChatGPT 审阅；结果回到程序后再进入原有门禁。

这与当前协议中“GitHub runner 负责机器发现与校验，assistant 负责语义主审和挑战复核”的分工相接近。改造重点是标准化交接，而不是把全部工作继续留在长对话里。fileciteturn55file0L2-L2

优点是先减少流程漂移，不急于更换判断来源。局限是：**仍然依赖 ChatGPT 参与，并没有变成完全独立的无人值守程序。**

同时，不能把 ChatGPT 订阅理解成脚本可直接调用的 API 额度；官方说明两者分别计费。这条路线不应靠假定存在一个免费脚本接口来设计。citeturn827080search2

### 路线 B：统一脚本＋本地模型

脚本把证据和规则发送给你自己机器上运行的模型，取得结构化审核结果，再进入相同的校验和发布环节。

这条路线可以不依赖 OpenAI 云端推理 API。Ollama 支持本地模式及结构化输出，llama.cpp 也提供本地模型服务。OpenAI 自己发布的 gpt-oss 也属于可在自有基础设施上运行的开放权重模型；它不是把当前 ChatGPT 的模型复制到本地。citeturn827080search0turn827080search4turn895810search1turn895810search5

这里“本地服务接口”只是程序与本机模型通信，不等于调用 OpenAI 的收费接口。**推理可以本地完成，但获取今天的新论文仍然需要联网和相应访问权限。**

这条路线最接近你说的“自己启动一个程序，完成日常抓取和判断”。不过，我尚未用你的论文样本测试本地模型，也没有据此确定适合的硬件配置，因此不能承诺它已经达到当前审核质量。

### 路线 C：统一脚本＋人工判断，不用模型

脚本收集候选和证据，生成审核界面，由你决定收录或排除，再自动执行后续检查和发布。

这可以完全取消模型依赖，但人工审核量不会消失。对于你要求的复杂边界判断，我不建议未经评测就把人工环节换成一组关键词规则，并称其为等效自动审核。

**选择可以概括为：保留现有判断来源，走 A；减少对云端模型的依赖，评测 B；完全不用模型，走 C，但保留人工。**

## 五、我建议把你的完整能力封装成什么样？

下面是拟议结构，不是已经实现、可直接运行的新命令：

```text
Gallery 单入口执行器
    │
    ├─ 读取并固定本轮规则、期刊表、纠错记录和代码版本
    ├─ 执行文献发现、去重、来源完整性检查
    ├─ 为每个 DOI 准备带来源的证据包
    ├─ 调用可替换的审阅后端
    │      ├─ 现有 ChatGPT 交接
    │      ├─ 本地模型
    │      └─ 人工审核
    ├─ 执行第一遍判断及挑战复核
    ├─ 运行独立校验器，保存 staging 和未决工作
    ├─ 在获准发布槽调用现有发布链
    └─ 核验线上结果，保存回执与恢复点
```

其中有四件事，我认为比“最终有几个脚本文件”更重要。

**第一，规则要可追溯，不能过度浓缩。**

收录契约、期刊启用日期、用户确认的 DOI 纠错、发布权限和既有审核案例，应当引用有版本的权威记录，而不是变成一段越来越长的提示词。当前能力登记册部分说明仍写着 15 本期刊，但当前正式期刊表已经含 JOC、共 16 本。这说明封装时必须核对真实依赖，不能把旧说明直接硬编码为新程序的事实。fileciteturn57file0L2-L2 fileciteturn61file0L2-L2

**第二，模型只给出可核验的判断结果，不直接拥有发布权限。**

建议每篇输出 DOI、主要贡献、制备转化、一般性证据、来源定位、第一遍结论、挑战结论和最终状态。模型输出 JSON 后，程序仍独立核对证据引用、候选集合和规则版本。结构化输出解决格式问题，不替代事实审核。

证据已经检查但不足，才是 `pending`；没有真正处理的任务要保留为 `unfinished`，不能伪装成审核完成。两次调用同一个模型，也不能写成“两个独立专家一致同意”。这些界线在你现在的审核契约和协议里已经明确，应完整保留。fileciteturn54file0L2-L2 fileciteturn55file0L2-L2

**第三，证据获取和收录判断必须分开。**

拿不到正文不能自动推断论文不合格；反过来，拿到了 TOC 或很多图片也不能自动推断论文合格。现有契约本来就把媒体交给 Tampermonkey/VPN Bridge，并规定缺 TOC 不阻挡正确文献卡片。封装应保留这个职责边界。fileciteturn54file0L2-L2

因此，单入口可以协调浏览器采集节点，但不能声称一个普通命令行脚本天然拥有校园 VPN、出版社登录态和所有浏览器权限。

**第四，失败恢复必须由程序负责。**

建议按 DOI、证据版本和规则版本保存进度。中断后只恢复未完成工作；已审核结果在证据和规则未变化时可以复用；发布失败则重试对应交付步骤，不重新抓一遍所有论文。程序还应保留现有 08:00/18:00 发布权限、并发保护、获准 DOI 清单和线上核验，不能为了“一键化”取消门禁。fileciteturn55file0L2-L2 fileciteturn60file0L2-L2

## 六、最稳的落地顺序：先封装流程，再评测替换模型

我不建议第一步就“把当前 GPT 换成本地模型”。那会同时改变流程和判断来源，出错后难以定位是哪一层退化。

第一步应当只统一入口、规则版本、证据格式、审阅结果格式和恢复机制，保留当前正式判断与发布路径。第二步让候选本地模型在旁路审阅同样的证据，不写生产。第三步才根据结果决定它可以独立承担哪些类别，以及哪些情况必须保留人工复核。

评测应使用你已经确认的正确收录、正确排除和边界纠错案例，再加一组没有参与规则调试的新论文。不能把历史 GPT 结论全部当作正确答案，用户后续确认的纠错必须优先。

重点看漏收、误收、证据引用是否真实、待核比例和实际处理耗时。**不能靠把困难论文全部放进 pending，制造“几乎不误判”的表面结果。**也不应只依据模型自报的置信度批准发布。

最终，我的建议是：**把你的业务方法沉淀为可移植的运行包，让模型成为可替换部件，而不是整个网站的唯一控制中心。**

所以答案不是“只能依赖云端大模型”，也不是“把现有脚本合并后就不需要智能判断”。更准确的是：

> **流程可以独立；规则可以保存；脚本可以统一；模型可以本地化。需要用真实论文验证的，是替换后的判断质量，而不是程序能否启动。**

本次完成的是核心链路核对和封装方案评估，尚未打包或测试独立执行器，也没有更改生产代码、抓取任务或发布流程。
