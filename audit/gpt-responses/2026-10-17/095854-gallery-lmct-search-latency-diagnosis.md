## 给用户的可见正文（预先持久化）
已定位到 Gallery 搜索链路中几个明确的性能问题。截图中的 `lmct` 检索不应该让整个结果区长时间空白。

**最直接的问题在前端：** 当前代码一开始搜索就清空文献卡片，显示“正在检索”，而且没有独立的加载超时保护。如果后台请求卡住，用户就可能一直看到这个界面。

进一步检查还发现：

1. 每次全库检索可能需要先检查 D1 索引状态。
2. API 请求失败时，会依次尝试备用域名和兼容接口，造成等待叠加。
3. 即使数据库已经返回匹配 DOI，前端仍需批量读取、验证文献分片，完成后才显示结果。
4. D1 不可用时，静态全库检索可能读取多个历史分片，进一步延长响应时间。

这些是代码中确认存在的耗时路径。**但还没有取得本次 `lmct` 搜索的实际网络耗时，因此不能断定其中哪一项占据了最多时间。**

我建议修复为：先展示可用的缓存候选并标明“部分结果”，保留旧卡片而不是清空；为网络请求设置总时限与可取消降级；对结果分片逐批展示，不再等全页验证结束；减少失败时重复串行请求；加上分段耗时统计和慢网络回归测试。

目标是正常网络下约 1–2 秒看到首批有效结果、约 3 秒完成常见查询；如果全库索引不可用，必须明确提示“结果不完整”，绝不能虚报 0 篇。这是拟议目标，还没有实测验证。

**目前只是核查，尚未修改或部署。** 按照项目的反馈审批规则，请回复“批准优化全库搜索速度”，我再实施并验证。
