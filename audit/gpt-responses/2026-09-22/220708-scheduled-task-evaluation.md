## 二、应当优先修正的问题

**1．最高优先级：真正的 Pages 发布门禁被跳过了。**

在 `.github/workflows/github-pages.yml` 中，“Enforce fixed literature publication slot”步骤带有 `if: ${{ false }}`，因此不会执行；部署 job 只依赖本工作流的 `build`，没有把独立的文献质量检查作为显式前置依赖。由此可见，不能把“质量检查存在”当成“质量检查失败就一定阻止上线”。这是本次发现最需要先修的配置问题。fileciteturn14file0L2-L2fileciteturn18file0L2-L2

建议恢复实际阻断能力，但不要简单禁止一切非08/18时段的界面或图片部署。正确区分应是：**文献数据未变，允许界面/媒体更新；文献数据发生变化，必须通过该发布槽位的审核和授权校验。**“这是图片恢复部署”的文字说明不能替代文献数据哈希比对。

与之配套，正式发布任务必须读取并更新 `audit/publication-release-state.json`。当前标记仍是 512 张卡片的 bootstrap 基线，校验器会逐文件核对受保护数据的 SHA；但现行发布任务提示词没有要求维护这个标记。需要把正式 review、生产数据与发布标记作为同一个原子提交发布，避免数据更新了、标记没跟上，或者反过来。fileciteturn15file0L2-L2fileciteturn13file0L2-L2

**2．必须区分“审核文件有效”和“允许发布”，明确阻止 pending。**

当前预发布校验器允许包含 pending 的完整审核文件返回成功，这作为“结构与记录完整性检查”本身可以成立。问题是正式发布任务列出的条件主要是“覆盖全部候选、双遍完成、分歧为零”，没有显式要求 `pendingCount=0`。两个审核遍次都判断 pending 时，同样可以做到“分歧为零”，当前那篇 CCS 文献正是这种情况。fileciteturn11file0L2-L2fileciteturn8file0L2-L2

建议把两个结果拆开：`reviewValid` 表示文件及证据记录有效；`publishable` 才表示准许发布。后者必须同时满足 `readyToPublish=true`、`pendingCount=0`、`remainingUnresolved=[]`、全部候选完成最终决定、双遍通过，以及快照和来源门禁一致。关键字段缺失应判定为无法验证，而不是默认成零。

按你现行的整批完整审核要求，只要仍有这 1 篇 pending，就应继续补证据或错过该槽位，不能把它当作已经排除，也不能自行改成“先发其他9篇”。

**3．正式审核校验器存在一个可导致误报失败的字段问题，staging 转正式 review 也需要固定转换程序。**

`validate-literature-quality-gate.mjs` 在构造 `all` 数组时，给复制出来的记录添加 `_decision`；但随后检查 challenge 一致性时，却遍历原始 `accepted/rejected` 数组并读取 `item._decision`。正常不带这个内部字段的正式审核记录，即使 `challengeDecision` 正确，也可能被判为不一致。这是本次静态代码检查发现的问题，尚未通过新的生产发布运行复现。fileciteturn7file0L2-L2

另外，当前 staging 使用 `decisions[]`，正式校验器读取的是 `accepted[] / rejected[] / pending[]`，还要求每条具有 `reason`。所以不能只把 staging 改名成 `review-*.json`；应使用固定转换程序，保留 DOI、证据、challenge、优先级和计数，并生成正式结构所需字段。建议一起加入“应通过的合法样例”和“必须拒绝的 pending/缺字段/计数不符样例”，而不是依赖每次执行任务临场组织 JSON。fileciteturn8file0L2-L2fileciteturn7file0L2-L2

**4．发布前校验与发布后验收需要明确顺序，不能依靠几个 workflow 同时启动。**

当前生产数据 push 会触发机器审计、文献质量检查和 Pages。文献质量检查又会访问已经部署的网站；如果它比部署先完成，就可能读取旧页面而报错。因此，把“仓库内审核一致性检查”和“部署后线上核验”混在一个并行任务中，会制造时序问题。fileciteturn6file0L2-L2fileciteturn12file0L2-L2fileciteturn7file0L2-L2

建议形成明确依赖：已冻结的审核输入 → 仓库内发布资格校验 → 固定槽位提交与部署 → 针对同一发布版本的线上 DOI/数量核验 → `synced`。后续新发现的候选可以进入下一槽位，但不应悄悄替换正在验收的审核基准。

还要避免假定“审计机器人写回文件后，会自动触发所有下游 push 工作流”。GitHub 官方明确说明，使用仓库 `GITHUB_TOKEN` 产生的普通 push 不会再次启动新的工作流。因此建议使用明确的工作流依赖或完成事件衔接，而不是碰运气等待下一次人工提交触发验收；这不需要让 ChatGPT 改用本地 Node 或依赖 `workflow_dispatch`。citeturn519853view1

## 三、保持现有频次，进一步提高稳定性

**审计触发与补审应更有针对性。** 机器审计目前使用全局 `cancel-in-progress: true`；主审核已经要求复用正常运行中的审计，但补审提示词没有同样明确的防重复触发约束。建议两者统一：先核对同一槽位的运行状态，正在运行则复用，失败或明确过期才重试；以“槽位＋输入快照”作为去重键，并保留带有效期的运行锁。fileciteturn6file0L2-L2

同时，应把审核绑定到不可变的 handoff SHA/提交，而不是只绑定会不断变化的 `unresolved-latest.json` 文件名。新增 DOI、实质性 metadata 变化和既有 pending 才进入补审；未变的已决记录保留有效证据。发布时仍须检查最新候选与已审集合是否一致，发现未审增量就 fail closed，不能用“冻结快照”作为漏审理由。

**时间与来源规则需要统一成可执行条件。** “足够新”目前仍有解释空间；代码又允许发布标记在槽位后20分钟内提交，而协议强调固定时点发布。应统一定义快照时效、审核截止、逻辑槽位和实际部署完成时间，不能让任务文字和校验器各用一套标准。这个20分钟不能由任务自行解释为随时补发许可。GitHub 的定时调度也可能延迟，不能把准点启动当作可靠性前提。fileciteturn13file0L2-L2fileciteturn1file0L2-L2citeturn519853view0

当前16本期刊的 sourceChecks 行虽然齐全，但状态是3本 checked、8本 blocked、5本 unavailable，不是16本出版社实时来源全部核验成功。应继续分开记录机器元数据来源健康与出版社页面核验；无法取得的计数保留未知，不能写成“0篇”。fileciteturn2file0L2-L2

**通知与状态汇总应围绕最终结果。** 当前任务配置显示，主审核开启了通知和邮件，补审与正式发布都没有开启。建议把通知重点放在正式发布成功、发布失败和仍需人工补证据，而不是主要通知中间步骤；发布后的异常监测可以做成只读核验，不再增加另一套抓取或补发任务。

状态文件也应收敛：目前 `prepublish`、`prepublishStaging` 等位置重复记录审核计数，历史 `lastWebsiteSync` 还保留503，而最新机器报告为512。这不直接证明网站丢卡，但说明不同用途的数字必须明确标注来源和版本，不能随意混用。建议保留一份当前槽位状态，以文件路径和 SHA 引用审核产物，并与“上次已验证生产版本”分开。fileciteturn2file0L2-L2

**我的建议顺序是：先修实际发布门禁和发布标记，再修 pending 放行条件与正式审核校验器，然后处理工作流依赖、审计去重及通知。** 现有时间安排暂不需要增加频次；当前最主要的问题不是任务太少，而是几处关键约束尚未在真正执行的代码里闭合。
